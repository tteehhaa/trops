## 이번 사이클에서 가장 값진 것 3가지

### 1. 테스트가 관계없는 섹션의 레이아웃 붕괴를 잡았다

진행상태 트래커를 `.steps`/`.step` 으로 썼는데, precheck.html 위쪽 「이용 방법」 3단계 섹션이 **그 두 이름을 이미 쓰고 있었다**(`.step { display: grid }`). 나중에 선언된 `display: flex` 가 그 그리드를 덮어써, **증상이 접수확인 화면이 아니라 관계없는 섹션에서 나타나는** 종류의 사고였다 — 눈으로 훑어서는 못 찾는다.

`.progress-*` 로 개칭하고, 「addProgress 가 붙이는 클래스는 `progress`/`progress-*` 뿐」 + 「이용 방법 `.step` 의 grid 가 살아 있는가」 두 단정을 박았다.

**교훈**: 큰 파일 하나에 CSS 가 모여 있는 구조에서는 새 클래스 이름을 정하기 전에 그 파일을 grep 해야 한다.

### 2. 배포 순서 의존성을 코드로 없앴다

`doc_type` 은 접수가 **실제로 insert 하는** 컬럼이라, 컬럼 없는 환경에 코드가 먼저 배포되면 PostgREST 가 PGRST204 로 거절해 **모든 접수가 502** 가 된다. 처음엔 "배포 전에 SQL 을 먼저 실행하십시오"를 문서에 적는 것으로 끝낼 참이었는데, 그건 사람의 기억에 프로덕션 가용성을 맡기는 것이다.

`precheck-schema.sql` 「0-F」 절이 **이미 그 원칙을 적어 두고 있었다** — 「마이그레이션을 잊었을 때 깨지는 것이 운영 도구 하나이지 접수 전체가 아니어야 합니다」. 그 원칙을 그대로 적용해, 「그런 칸 없다」는 응답에는 그 칸을 떼고 한 번 더 넣도록 했다(재시도 1회, 중복키·500 같은 진짜 실패는 제외, 폴백 사용 시 로그에 명시).

**교훈**: 저장소가 이미 적어 둔 원칙을 먼저 찾아볼 것. 새로 판단할 필요가 없었다.

### 3. md 문구를 그대로 쓰면 거짓말이 되는 자리를 찾았다

md §5-1 10번은 3단계 라벨을 「접수됨 → 검토중 → 전달완료」로 지정했다. 그런데 `status='in_progress'` 는 **사람이 아직 손대지 않은 건에도 붙는다**(기존 `statusLabel` 주석이 실측으로 남겨 둔 사실). 그걸로 "검토중"을 말하면 아무도 안 보는데 보고 있다고 말하는 것이 된다.

md 문구는 그대로 쓰고, **근거만** 판정층 `precheck_nda_run` 행 존재 여부로 바꿨다. 그 행은 대조 엔진이 실제로 돈 뒤에만 생기므로 "검토 단계에 들어갔다"가 사실이 된다. md 요구와 저장소 원칙을 둘 다 지켰다.

## 🔴 라이브 실측으로 드러난 구조적 사실 — 9번은 지금 발화할 수 없다

프로덕션 `intake` 12행이 **전부 `free/none`** 이고 `awaiting_payment` 는 0건이다. 결함이 아니라 설계다:

```
유상 과금 게이트: isPrecheckPaidChargeEnabled() === false
막고 있는 것    : ['paid_charge_enabled', 'S62-44', 'S62-03']
```

`api/intake.js` 가 유상 경로를 접수 시점에 거절하므로(`rejectIfChargeBlocked`) `intake_path='paid'` 행이 생기지 않는다. `awaiting_payment` 는 유상 경로에서만 나오는 상태이므로, **과금 게이트가 열리기 전까지 리마인드 후보는 구조적으로 0건**이다.

- 배치는 매일 정상적으로 돌아 0건을 보고한다(오늘 실측이 그것을 보였다)
- **게이트가 열리는 날 자동으로 살아난다** — 추가 코드 작업 없음. 그날 첫 실행 전에 `npm run remind:preview` 한 번만 돌릴 것
- 반면 **8번은 지금 발화한다** — `sendIntakeMails` 안에 있고 무상 경로가 그 함수를 부르므로, 다음 무상 접수의 확인메일에 기한관리 링크가 들어간다
