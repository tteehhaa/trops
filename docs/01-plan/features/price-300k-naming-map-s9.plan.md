앞 사이클(`naming-consistency-s9`)이 미결로 남긴 두 항목이 이번 스코프다.

| 미결 | 내용 | 이번 처리 |

| ② | 플랜 카드가 **선택 전부터** 가격을 그려 둠 — 과금 게이트를 여는 순간 실제 문제 | 노출 자리를 좁히고 검사로 못질한다 (§1-2) |

여기에 두 건이 더 붙는다 — 상품명 통일(§2)과 지도 예시데이터 되돌림(§3).

## 1. 가격 — ₩99,000 → ₩300,000 (VAT 별도)

**근거**: 흐름 md §4. 「셀프서브는 지금부터 ₩300,000(VAT별도)을 쓴다」 + 「99,000원
헤드라인 폐기 확정 — legal-adjacent 카테고리에서 저가는 신뢰저하 리스크가 더 크다」.

### 1-1. 값을 옮기는 순서 (⛔ 순서를 바꾸지 않는다)

trops_a `lib/config/cross-repo-values.ts` 가 이 저장소의 `api/_payment.js` 에 대해
적어 둔 문장이 순서를 정한다 — **「실제 청구 금액이다 — 표시보다 먼저 고친다」**.
그래서 표시(HTML)를 먼저 고치지 않는다.

```
① trops_a  lib/payment/precheck-paid-gate.ts   PRECHECK_PRICE.launchKrw   ← 정본
② trops_a  lib/config/cross-repo-values.ts     원장 기록 (RESOLVED_DECISIONS)
③ 이 저장소 api/_payment.js                     PRICE  ← 실제 청구 금액
④ 이 저장소 precheck.html                        표시 3자리
⑤ 이 저장소 scripts/verify-deployment.js         R1-취소선 기대값
```

`test/precheck-charge-gate.test.js` 「정가·런칭가가 정본과 같다」가 ①↔③ 드리프트를
읽는다 — 이 검사는 옆 저장소가 있을 때만 돌므로(CI 에서는 skip), **여기만 고치면
로컬만 빨개지고 CI 는 조용히 통과한다.** 그것이 이 검사가 막으려던 상태다.

### 1-2. 노출 시점 — 어디까지가 이 저장소의 몫인가

요청은 「접수 → 대조 실행 → 결과 티저(차이 개수) → 그 다음에 가격」이다.
**이 저장소에는 대조 결과가 없다.** 대조·판정은 trops_a 이고, 이 저장소는 접수·저장·
알림·결제 처리만 담당한다(`api/_payment.js` 머리주석의 경계 선언).

더 큰 문제는 그 순서가 **흐름 md §3 과 반대**라는 것이다:

```
흐름 md §3    접수 → 결제(₩300,000, AI 실행 전) → AI 대조 실행
요청          접수 → AI 대조 실행 → 결과 티저 → 결제
```

md §0-2 는 「결제는 **AI 실행 전**」을 원칙으로 못질해 두었다(비용 노출 없음).
요청안은 미결제 건에도 AI 비용을 먼저 쓴다 — 상품 원가 구조가 바뀌는 결정이다.

→ **이번 사이클은 요청자가 제시한 대안("최소한 선택 전부터 가격이 안 보이게")까지만
한다.** 전체 재구조화는 `docs/03-analysis/price-gate-teaser-restructure.md` 로 분리해
설계·전제·비용을 적고 결정을 올린다.

이번에 실제로 하는 것:

- 가격 문자열이 **`#pay-area` 안에만** 있게 한다 (결제수단을 고른 뒤에만 열리는 영역)
- 숨김이 CSS(`.plans { display:none }`) 한 겹에 의존하던 것을 **검사로 못질**한다 —
  지금은 CSS 를 지우는 순간 선택 전 가격이 되살아나고 아무도 모른다
- `VAT 별도`를 가격 옆에 병기한다 (md §4 표기 그대로)

## 2. 상품명 — 「수출 사전점검」으로 통일
