## M-3 — 「불가」 비과금

### 새 게이트를 만들지 않고 기존 게이트를 두 축으로 늘렸습니다

`api/_precheck-charge-gate.js` 에 **축 ②** 를 붙였습니다.

| | 축 ① (종전) | 축 ② (신설) |
|---|---|---|
| 묻는 것 | **유상 판매를 개시해도 되는가** | **이 접수 한 건을 과금해도 되는가** |
| 건별로 다른가 | 아니오 | 예 |
| 값의 출처 | trops_a 정본의 사본(드리프트 검출 있음) | 브라우저가 신고한 기계적 사실 |
| 사유 코드 | `paid_charge_enabled` · `S62-44` · `S62-03` | `ineligible:text-layer-absent` |

**왜 병렬 게이트를 만들지 않았는가**: 결제 경로에서 「막혔나」를 묻는 자리가 둘이 되면,
새로 생기는 결제 경로가 한쪽만 부르고 지나갑니다. 던지는 함수 하나
(`assertPrecheckChargeAllowed`)가 두 축을 함께 보게 두면 호출부는 이유를 몰라도 되고,
사유가 늘어도 호출부를 고치지 않습니다.

**축 ①의 사본 성질을 건드리지 않았습니다** — `precheckChargeBlockers()` 는 그대로입니다.
정본 드리프트 테스트 4건이 계속 같은 것을 보고 있습니다.

### 🔴 신고값은 한 방향으로만 움직입니다

브라우저가 보내는 `detection.pdfTextLayer` 는 **차단 사유를 더할 수만 있고 축 ①을 열지
못합니다.** 그래서 값이 고쳐져 와도 위험한 방향(막혀야 할 건이 과금되는 방향)으로는
가지 않습니다. `'present'` 로 위조해도 축 ①이 그대로 막습니다 —
`test/precheck-charge-gate.test.js` 「신고값은 축 ①을 열지 못한다」가 이것을 단정합니다.

### e2e 확인 — 실제 브라우저 · 실제 라우트

⚠️ **지금 라이브 상태로는 이 기능을 확인할 수 없습니다.** 축 ①이 모든 유상 건을 막고
있어서 「불가라서 막혔다」와 「아직 안 열려서 막혔다」가 구분되지 않습니다. 그래서
**개시 게이트를 잠깐 열어 둔 하니스**를 세우고 확인했습니다(파일 상수는 고치지 않고
객체 속성만 뒤집었다가 되돌립니다 — 고치면 정본 드리프트 테스트가 red 를 내야 하고,
그건 이 확인이 잴 것이 아닙니다).

하니스는 `dist/` 산출물을 서비스하고 **진짜 `api/intake.js` 를 마운트**했습니다
(Supabase·Resend 만 가짜). 「접수가 실제로 완료되는가」를 화면에서 눌러 확인했습니다.

| 확인 | 방법 | 결과 |
|---|---|---|
| 개시 열림 → 유상 선택 가능 | 결제위젯이 그려지고 버튼이 `₩99,000 결제하고 보내기` | ✅ |
| **텍스트 레이어 없는 PDF 업로드 → 결제 진입 차단** | `plan-paid` `disabled=true` · `pay-area` 숨김 · 무상으로 전환 · 버튼 `₩0으로 보내기` | ✅ |
| 안내가 뜨는가 | 카드 문구 = M-1 지정 문장 그대로 | ✅ |
| **화면 잠금을 지나쳐 서버로 직접 보낸 경우** | `403 ineligible-not-charged` · `blockers=["ineligible:text-layer-absent"]` | ✅ |
| 그때 저장·주문·결제 호출 | **Supabase 쓰기 0건 · 주문 발급 0건 · 토스 호출 0건**(하니스 로그) | ✅ |
| 파일을 텍스트 PDF 로 바꾸면 | 잠금이 풀리고 유상 카드가 되돌아옴(`바로 신청`) | ✅ |
| 콘솔 | JS 오류 0건 · 처리되지 않은 거절 0건 (favicon 404 와 의도한 403 뿐) | ✅ |

자동 회귀로도 박아 두었습니다 — `test/precheck-charge-gate.test.js` 에 축 ② 8건 추가
(전체 25건 통과). 그중 두 건이 이 배치의 핵심 단정입니다:

- 「개시가 열려도 「불가」 건은 막힌다 — 사유종류가 갈린다」
- 「**「불가」라도 무상 접수는 그대로 완료된다**」 ← M-1 의 「접수 거부 금지」

### 환불 트리거 — **운영자 수동 실행 + 코드가 트리거 지점을 제공**

`scripts/refund.js` (본체 `api/_refund.js`).

```
node --env-file=.env.local scripts/refund.js <orderId> --reason "판별 불가"          미리보기
node --env-file=.env.local scripts/refund.js <orderId> --reason "판별 불가" --apply  실제 취소
```

**왜 자동이 아닌가**: 「판별이 뒤집혔다」를 이 저장소가 알 방법이 없습니다 — 처리 등급을
받아오는 인터페이스가 trops_a 와 아직 없습니다(M-2 스코프 아웃과 **같은 원인**입니다).
없는 인터페이스를 메우려고 이 저장소가 「불가인지」를 스스로 정하기 시작하면 그것이
곧 이중구현이고 경계 위반입니다. 그래서 **판단은 사람, 실행은 코드**로 갈랐습니다.

**왜 「토스 대시보드에서 손으로 취소」로 두지 않았는가**: 그러면 돈은 돌아가지만 우리 DB 는
`payment_status='paid'` 로 남습니다 — 이용자의 접수 확인 화면이 「결제 완료」를 계속
보여 주고, 환불 이력 어디에도 근거가 없습니다. **돈과 기록이 갈라지는 것이 수동 취소의
실제 위험**이고, 이 스크립트가 그 둘을 한 번에 묶습니다.

순서가 설계입니다 — ① 환불 컬럼 선행 검사(**돈을 건드리기 전에**) → ② 상태 확인 →
③ 멱등키 붙여 전액 취소 → ④ `payment_status='refunded'`·`refunded_at`·`refund_reason` 기록.

`test/refund.test.js` 11건 통과. 그중:

- 「환불 컬럼이 없으면 취소하기 전에 멈춘다」 — 취소 호출 0건을 단정
- 「전달까지 끝난 건은 `status` 를 덮지 않는다」 — `delivered` 를 지우면 환불규정 §02 기준선이 사라집니다
- 「이미 환불된 건은 다시 취소하지 않는다」 · 「`--apply` 없이는 아무것도 취소하지 않는다」

**남은 일 1건 — 이용자 안내 메일은 아직 자동이 아닙니다.** 스크립트가 실행 끝에
「누구에게 알려야 하는지」를 출력하고, 그 사실을 출력으로 명시합니다.

### 스키마 — 가산만

`precheck-schema.sql` 「0-F. 환불 기록 컬럼」 — `refunded_at` · `refund_reason` · 부분 색인.
`payment_status` 에 `'refunded'` 는 이미 있었으므로 **제약 변경 0건**입니다.

⚠️ **이 절을 실행하지 않아도 접수·결제는 그대로 동작합니다.** 접수 경로가 이 컬럼을 쓰지
않게 둔 것이 의도입니다 — 마이그레이션을 잊었을 때 깨지는 것이 운영 도구 하나이지
접수 전체가 아니어야 합니다. 환불 스크립트만 선행 검사에서 멈추고 이 절을 가리킵니다.

## M-1 — 텍스트 레이어 감지

### 감지 방법 — **라이브러리 없이 PDF 구조 표지 3개**

`precheck.html` 의 `<text-layer-detect>` 블록. 브라우저에서만 돕니다.

1. 원시 바이트에서 `/Font` · `/ToUnicode` · `BT…Tj/TJ/Tf` 를 찾습니다 → 하나라도 있으면 `present`
2. 없으면 **FlateDecode 스트림을 풀어 다시 찾습니다** — 현대 생산기(PDF 1.5+)는 글꼴 사전을
   압축 객체스트림(`/ObjStm`)에 넣어서, 원시 바이트만 보면 **글자 있는 PDF 를 없다고 말합니다**
3. 셋 다 없으면 `absent`
4. 못 정하면 `unknown` → **안내하지 않습니다**(암호화 PDF · 못 푼 스트림 · PDF 아닌 파일)

### 후보였던 pdf.js 를 쓰지 않은 근거

pdfjs-dist(Apache-2.0)는 표준이고 정확합니다. 쓰지 않기로 한 이유 셋:

| 이유 | 내용 |
|---|---|
| **무게** | `pdf.min.mjs` + worker 합계 약 1.4MB. 번들러가 없어 CDN 아니면 원본을 통째 커밋해야 합니다 |
| **결제 화면** | 이 페이지에는 결제위젯이 이미 붙어 있습니다. 동적 `import` 에는 SRI 를 걸 수 없어 무결성 확인 없이 제3자 원본이 늘어납니다 |
| **필요한 것이 판독이 아님** | 글자를 뽑아 쓰지 않고 「있나 없나」만 답합니다. 그 답에는 구조 표지 3개로 충분합니다 |

⛔ **되짚을 조건**: 실측에서 오탐(글자 있는 PDF 를 `absent`)이 나오면 그때 pdf.js 로 올립니다.
지금 근거는 아래 표본 전건 일치입니다.

### 오탐·누락 실측

`test/text-layer-detect.test.js` 11건 통과. 표본은 커밋하지 않고 테스트가 만듭니다
(macOS `cupsfilter`·`sips` 산출물 2종 + zlib 로 조립한 4종).

| 표본 | 무엇 | 기대 | 결과 |
|---|---|---|---|
| `real-text.pdf` | **실제** 텍스트 PDF (cupsfilter) | present | ✅ |
| `real-scan.pdf` | **실제** 랩스터 PDF (같은 문서를 sips 로 이미지화) | absent | ✅ |
| OCR 표본 | 이미지 + 비가시 텍스트(`3 Tr`) | **present** | ✅ **오탐 0** |
| 객체스트림 표본 | `/Font` 가 압축 안에만 있는 PDF | present | ✅ |
| 이미지 전용 | 글꼴·텍스트 연산자 0건 | absent | ✅ |
| 암호화 · 비PDF · 빈 파일 | 못 정하는 경우 | unknown | ✅ |
| 못 푼 압축 스트림 | 근거가 없는 경우 | unknown | ✅ |

**판별 기준이 「스캔인가」가 아니라 「텍스트 레이어가 있는가」라는 것**을 OCR 표본이 지킵니다 —
그 표본에서 안내가 뜨면 red 입니다.

브라우저 실측(하니스):

| 확인 | 결과 |
|---|---|
| 랩스터 PDF 업로드 → 안내 표시 · 문구 = 지정 문장 그대로 | ✅ |
| 안내 색 | `#E2E8F0` 테두리 / `#F1F5F9` 배경 — **경고색 아님** | ✅ |
| OCR 표본 · 실제 텍스트 PDF · 객체스트림 PDF 3개 동시 업로드 | **안내 없음** | ✅ |
| 3개 중 1개만 걸린 경우 | 걸린 파일 이름을 함께 표시(「이 파일」이 어느 것인지) | ✅ |
| **[이대로 진행하기] → 접수** | `201` · 저장·업로드·확인메일까지 실제 수행 | ✅ |
| [다른 파일 올리기] → 텍스트 PDF | 안내 내려가고 잠금도 풀림 | ✅ |

🔴 **[이대로 진행하기]뿐 아니라 안내를 그냥 두고 보내기를 눌러도 접수는 진행됩니다.**
안내가 접수를 막고 있지 않으므로 「진행하기」가 내리는 것은 안내뿐입니다. 막는 것은 과금입니다.

### 감지 대상은 PDF 뿐입니다 — 이미지·DOCX 는 등급을 정하지 않습니다

「이미지 파일은 글자가 없으니 불가」라고 정하는 것은 **등급 판정**입니다.
「PDF 에 텍스트 레이어가 있는가」는 **구조 메타데이터의 사실**입니다. 앞의 것은 trops_a
소관이고 뒤의 것만 여기서 봅니다. 그 선을 넘지 않았습니다.

## M-2 — 처리 등급 사전 안내 · ⛔ **스코프 아웃**

### 먼저 확인한 것 — 등급을 받아오는 인터페이스가 이 저장소에 있는가

**없습니다.** 실측 근거:

| 찾은 것 | 결과 |
|---|---|
| 이 저장소가 trops_a·`app.trops.kr` 를 런타임에 부르는 곳 | **0건** (`trops_a` 문자열은 전부 주석) |
| `precheck-schema.sql` 의 등급 컬럼 | **0건** |
| 접수 조회 응답(`GET /api/intake?r=`)의 등급 필드 | **0건** (status·paymentStatus·deliveredAt 등 14개 중 없음) |
| trops_a 쪽 노출 라우트 | `app/api/` 에 cron·briefing-push 뿐 — 등급을 내주는 라우트 없음 |
| trops_a 쪽 「자동/부분/불가」 산출물 | `lib/precheck/classifier.ts` 는 **항목 단위 상태**(미기재·공란·기준-상이)이고 **case 단위 처리 등급이 아닙니다** |

PRD-62 §3-2 가 같은 구조적 공백을 이미 적어 두었습니다 —
「`main_web_page` 에서 이 함수를 호출할 수 없다 — 그리고 그것이 문제로 남는다 … 미결이며
유상 전환 착수 시점의 선행 조건이다 → **S62-82**」.

### 그래서 코드를 건드리지 않았습니다

인터페이스가 없는 상태에서 등급을 표시하려면 이 저장소가 등급을 **스스로 계산**해야 하고,
그것이 곧 이중구현이며 경계 위반입니다. 지시대로 스코프 아웃했습니다.
**이번 배치에서 M-2 가 빠진 것은 실패가 아니라 정상적인 결과입니다.**

⚠️ 문구 3종(자동·언어·텍스트레이어)도 넣지 않았습니다. 「불가·텍스트레이어」 문구만은
M-1 이 이미 같은 문장으로 띄우고 있으므로, 세 벌 중 하나는 실질적으로 서 있습니다.
「불가·언어」는 넣지 않았습니다 — 언어 판별 자체는 클라이언트에서 기계적으로 가능하지만,
그것을 **등급으로 표시**하는 순간 등급 축을 이 저장소가 갖게 됩니다.

### 다음 세션에 전달할 질문 (trops_a 와 확정 필요)

1. **등급의 정본이 어디인가** — `자동 / 부분 / 불가` 를 case 단위로 확정하는 함수·타입이
   trops_a 에 이미 있습니까? (`lib/precheck/classifier.ts` 는 항목 단위이고 case 등급이
   아닌 것으로 읽었습니다. 없다면 앞단이 표시할 것 자체가 아직 없습니다.)
