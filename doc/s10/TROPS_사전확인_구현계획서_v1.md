## §1 삽입 지점 — 파일·요소 단위

### 1-1. 신규 파일 2개

| 파일 | 역할 |
|---|---|
| `check.html` | 사전 확인 3문항 + 결과 화면 (S1~S4) |
| `api/prestep.js` | 세션 저장 엔드포인트 |

`check.html` 하나에 전 단계를 담습니다. 문항 전환은 클라이언트에서 섹션 토글(기존 `.feat-panel` `hidden` 토글 패턴과 동일한 방식). 페이지 이동 0회 = 체감 속도 확보.

### 1-2. `index.html` 수정 지점

라이브 코드에서 `/precheck`를 가리키는 요소는 **6곳**입니다. 전부 바꾸지 않습니다.

| # | 위치 | 현재 | 조치 |
|---|---|---|---|
| 1 | 히어로 `#hero-cta` | `href="/precheck"` 「비교해 보기」 | 🔴 **여기만 손댐** — §1-3 |
| 2 | `#feat-precheck-panel` 내 버튼 | `/precheck` | 유지 (제품 설명 맥락. 탭을 열어본 사람은 이미 이해한 상태) |
| 3 | `#feat-buyer-panel` 내 버튼 | `/precheck` | 유지 |
| 4 | `.act` 섹션 CTA | `/precheck` 「비교해 보기」 | **선택** — §13 미결 |
| 5 | `.how` 섹션 텍스트 링크 | `/precheck` | 유지 |
| 6 | 푸터 링크 | `/precheck` 「수출 사전점검」 | 유지 (정책·상품 링크) |

#### 위상 원칙 — 왜 히어로만인가

방문자는 페이지를 읽어 내려가며 계속 정보를 얻습니다. 제품 탭에서 무엇을 해주는지 보고, 결과지 이미지를 보고, 근거 섹션까지 읽습니다. **그래서 아래로 갈수록 사전 확인의 값은 떨어지고 직행의 값은 올라갑니다.** 근거까지 다 읽고 마감 CTA를 누른 사람에게 「지금 어느 쯤에 계신가요?」를 묻는 것은 이미 답을 아는 사람에게 묻는 일입니다.

**사전 확인 = 첫인상 담당 하나. 나머지는 전부 지름길.**

전면 치환이 깨뜨리는 것 두 가지:

| | |
|---|---|
| **문구가 무너짐** | 지금은 히어로만 「30초 만에 알아보기」, 나머지 5곳은 「비교해 보기」라 **문구가 다르니 목적지가 다른 것이 자연스럽습니다.** 전면 치환하면 제품 설명을 읽은 사람에게까지 「30초 만에 알아보기」가 뜨는데 맥락이 안 맞고, 문구를 「비교해 보기」로 둔 채 목적지만 바꾸면 **같은 문구인데 어떤 건 문항이 뜨고 어떤 건 안 뜨는** 더 나쁜 상태가 됩니다 |
| **관문이 됨** | 페이지의 모든 문이 사전 확인이면, 형식적으로 「차단 금지」에 안 걸려도 체감상 걸립니다. "뭘 답해야 통과되는구나"로 읽힙니다 |

### 1-2b. 신설 1곳 — QnA 「NDA가 뭔가요?」 ✅ 대표 결정

치환이 아니라 **비어 있던 자리에 놓는 것**이라 CTA 개수 경쟁이 없습니다.

현재 `#qa-1` 답변은 NDA를 설명하고 끝나며 **다음 행동이 없습니다.** 그런데 이 항목을 여는 사람이 정확히 사전 확인의 대상입니다 — 자기가 뭘 모르는지 모르는 사람.

```html
<div class="qans" id="qa-1">
  <p>비밀유지계약서(Non-Disclosure Agreement)입니다.</p>
  <p>거래 얘기를 본격적으로 시작하기 전에…</p>
  <p><a href="/check">지금 어디쯤이신지 확인해 보실 수 있습니다 →</a></p>
</div>
```

🔴 **배치 조건: 답변 본문에 엮지 말고 독립된 마지막 `<p>` 한 줄로.**
랜딩 QnA는 수정이 계속되는 중이고 나중에 교체 예정입니다. 독립 줄로 두면 **답변 본문을 통째로 갈아끼워도 이 줄만 남기면 되어 재작업이 0**입니다. 문장 안에 섞으면 그때 문장을 다시 짜야 합니다.

「NDA를 안 쓰는 업계인데요?」(`#qa-2`)도 같은 성격이지만 **한 섹션에 하나만** 둡니다.

### 1-3. 히어로 CTA — 치환 방식 ✅ 대표 결정

**CTA 개수는 3개 그대로.** 추가하지 않고, **첫 번째 버튼의 목적지만 바꿉니다.** 사전 확인은 새 선택지가 아니라 **기존 「비교해 보기」 경로의 초입**입니다.

| | 현재 | 변경 후 |
|---|---|---|
| 주 CTA | `[비교해 보기]` → `/precheck` | **`[30초 만에 알아보기]` → `/check`** |
| 보조 | `[문의하기]` → `#interest` | 그대로 |
| 텍스트 | `기한관리 미리보기` | 그대로 |

```html
<div class="cta-row">
  <a id="hero-cta" class="btn btn-primary btn-full" href="/check">30초 만에 알아보기</a>
  <a class="btn btn-secondary btn-full" href="#interest" data-purpose="inquiry">문의하기</a>
  <button class="btn btn-text" type="button" data-timeline-open aria-controls="feat-timeline-panel">기한관리 미리보기</button>
</div>
<p class="hero-note">로그인 없이 바로</p>
```

`.hero-note`「로그인 없이 바로」는 두 경로 모두에 참이라 그대로 둡니다. **마크업 변경은 `#hero-cta` 한 줄의 `href`와 텍스트뿐입니다.**

#### 「바로 비교해 보기」가 이동하는 자리

히어로에서 사라진 직행 경로는 **사전 확인 흐름 안쪽**으로 들어갑니다.

| 위치 | 문구 | 목적지 |
|---|---|---|
| 문항 화면 S1~S3 상시 링크 (G1) | **「바로 비교해 보기」** | `/precheck` (파라미터 없음) |
| 결과 화면 S4 블록3, 서류 있음 | **「이 서류 비교해 보기」** | `/precheck?pre=…&docs=…` |
| 결과 화면 S4 블록3, 서류 없음 | 「NDA를 받으시면 그때 보내주세요」 | 알림 등록 |

**문구 근거**: 「**바로**」가 문항을 건너뛴다는 뜻을 혼자 감당합니다. 결과 화면 쪽은 「**이 서류**」가 방금 답한 내용을 가리키므로 「바로」를 붙이지 않습니다. 두 문구가 랜딩의 「비교해 보기」와 같은 동사를 쓰므로 어휘가 갈리지 않습니다(랜딩=「비교」/앱=「대조」 규칙 유지).

#### S1~S3 상시 링크의 배치 ✅ 대표 결정

**문항 위, 진행표시(1/3) 오른쪽.** 문항 아래가 아닙니다.

```
┌────────────────────────────────────────┐
│  1/3                   바로 비교해 보기 → │ ← 여기
│                                        │
│  Q1. 지금 어느 쯤에 계신가요?            │
│  가장 최근에 있었던 일 하나만 골라주세요. │
│  ○ ○ ○ ○ ○ ○                           │
└────────────────────────────────────────┘
```

| | |
|---|---|
| **왜 위인가** | 사람은 화면을 위에서부터 읽습니다. 탈출구가 아래에 있으면 **문항을 다 읽고 짜증이 난 뒤에** 발견합니다. 위에 있으면 짜증이 나기 전에 지나가고, 비용이 「클릭 1번」으로 줄어듭니다 |
| **왜 텍스트 링크 유지인가** | 버튼(`.btn-secondary`)으로 만들면 서류가 없는 사람·뭘 모르는 사람까지 눌러버려 사전 확인이 존재할 이유가 없어집니다. **위치만 올리고 형태는 낮게** 두는 것이 균형점 |
| **더 올릴지 판단하는 신호** | ① `completed_step=0` 비중이 높음(들어와서 첫 문항에 답도 안 하고 나감) ② 정성 관찰에서 서류 가진 사람이 화면을 훑으며 망설임. 둘 중 하나라도 잡히면 **버튼화가 첫 조정 수단** — 히어로를 되돌리기 전에 이것부터 |

#### 이 방식의 득실

| | |
|---|---|
| ✅ 얻는 것 | 히어로가 지금과 똑같이 유지됨(구조 변경 0). 사전 확인이 **선택지 하나 더**가 아니라 **같은 길의 앞부분**으로 읽힘 — 「스텝이 늘었다」는 인상 자체가 생기지 않음 |
| 🟡 잃는 것 | **히어로에서 직행 버튼이 사라집니다.** 준비된 사람은 화면 하나·클릭 하나를 더 거칩니다 |
| 완화 | 랜딩의 나머지 `/precheck` 링크 **5곳이 그대로 살아 있습니다**(제품 탭 2곳·마감 CTA·HOW 텍스트링크·푸터). 직행 경로가 페이지에서 사라지는 것이 아니라 **히어로에서만 빠지는 것**입니다 |
| 관찰 | 정성 관찰 5명에서 **「서류를 이미 손에 든 사람이 문항을 성가셔하는지」**를 반드시 볼 것. 성가셔하면 S1 상시 링크의 위계를 올리는 것이 첫 조정 수단(히어로를 되돌리기 전에) |

### 1-4. D7 실행 대상 위치 (실측)

「수출」이 박힌 자리를 전수 확인했습니다.

| 위치 | 현재 | 교체 |
|---|---|---|
| 히어로 `.eyebrow` | 수출을 앞두고 | 해외 거래를 앞두고 |
| 히어로 `h1` | 첫 **수출**이라<br>무엇부터 봐야 할지 모르겠다면. | 첫 **해외 거래**라… |
| 푸터 `.footer-tag` | 수출을 앞두고 | 해외 거래를 앞두고 |
| `<title>` | 첫 수출, 무엇부터… | 첫 해외 거래, … |
| `meta description` | 첫 수출이라… | 첫 해외 거래라… |
| `og:description` | — **「수출」 없음** | **대상 없음 — 교체하지 않음** |
| `og:title` | 첫 수출, … | 첫 해외 거래, … |

**D7 실제 교체는 6곳입니다.**

🔧 **정정 (2026-08-15).** 이 표는 원래 `meta description`과 `og:description`을 한 행에 묶어 **둘 다 「첫 수출이라…」를 담은 것처럼** 적었고, 그래서 대상이 7곳으로 읽혔습니다. **`og:description`에는 애초에 「수출」이라는 낱말이 없었습니다.** `index.html` 상단이 스스로 밝힌 규칙 때문입니다 — `description = 헤드라인 + 리드`, **`og:description` = 리드**. 「첫 수출이라…」는 헤드라인 쪽 문장이므로 리드만 담는 `og:description`에는 들어갈 자리가 없었습니다. 실제로 D7 커밋(`878c393`)이 건드린 곳은 위 표의 나머지 **6곳**뿐이고, `og:description`은 손대지 않았습니다.

**교체하지 않는 것**: 푸터 `.footer-meta`「수출 거래 확인과 기한 관리」·법정 고지문·상품명 「수출 사전점검」(제품 탭·푸터 링크). 상품명 유지 근거는 설계 기록대로 — 이탈은 첫 화면에서 일어나고, 결제창 도달자는 이미 확신이 선 상태입니다.

⚠️ **`.stories-sec`·`.story-body`에도 「첫 수출이라면 원래 다 낯선 것들입니다」가 있습니다.** 여기는 위로 문안이라 「첫 해외 거래라면」으로 함께 가는 게 자연스럽지만, 마케팅 확정본 문안이라 **판단을 넘깁니다**(§13).

## §2 페이지 구조 결정

**`/check` 별도 페이지로 신설합니다.** 모달·인라인 섹션이 아닙니다.

| 근거 | |
|---|---|
| 1 | 기존 관례와 일치 — `/precheck`·`/privacy`·`/refund` 전부 별도 경로. 모달은 이 사이트에 선례가 0 |
| 2 | **이탈 지점 계측이 가능해짐** — 별도 페이지면 진입 자체가 이벤트. 모달이면 분석 도구 없이 진입 수를 셀 방법이 없음(§0에서 분석 도구 부재 확인) |
| 3 | 뒤로가기가 자연스럽게 작동 — 모달은 뒤로가기 처리를 직접 구현해야 함 |
| 4 | 공유·재방문 가능한 URL이 생김 |

`check.html`은 `index.html`의 인라인 `<style>` 중 필요한 부분만 복사합니다(빌드 도구가 없어 CSS 파일 분리가 오히려 구조 변경). 복사 대상은 §7 참조.

|---|---|---|
| `session_key` 생성 | `check.html` 최초 진입 시 `crypto.randomUUID()` | 서버 왕복 불필요 |
| 저장 위치 | **`sessionStorage`** | 쿠키는 이 사이트에 사용 선례 0 + 동의 절차가 붙음. 개인정보가 아니라 익명 난수라 동의 대상도 아님 |
| 수명 | 탭 세션 | 새로고침에는 답이 보존되고, 탭을 닫으면 새 세션. **의도된 동작** — 며칠 뒤 재방문자는 새 세션이 맞음 |
| 뒤로가기 | 이전 문항으로. 답은 sessionStorage에서 복원 | |
| 중복 진입 | 같은 탭에서 다시 들어오면 **기존 세션 이어받기**(`session_key` 유지, 답 복원). 새 레코드 만들지 않음 | 한 사람이 두 건으로 세지는 것 방지 |
| 결과 화면 재방문 | 답이 남아 있으면 결과 화면부터 표시 | |

## §4 API 계약

### 4-1. 저장 시점 — 문항별 저장이 필수인 이유

분석 도구가 없으므로(§0), **DB에 남는 것만이 지표입니다.** 마지막에 한 번만 저장하면 **이탈자는 레코드 자체가 생기지 않아** `completed_step`·`exited_via`가 영원히 측정 불가입니다. 설계서 §6의 지표 전부가 무의미해집니다.

→ **문항 응답마다 upsert.** 호출 3~4회.

### 4-2. `POST /api/prestep` — 프록시 (main_web)

🔴 **화면은 `trops.kr`, 저장소는 `app.trops.kr`로 도메인이 다릅니다.**

| 안 | 방식 | 판정 |
|---|---|---|
| A | 브라우저 → `app.trops.kr/api/prestep` 직접 | CORS 설정 필요. 방문자 브라우저가 앱 도메인을 직접 두드림 |
| **B ✅ 채택** | 브라우저 → `trops.kr/api/prestep` → **서버가 trops_a로 전달** | 브라우저는 `trops.kr`만 상대 → **CORS 불필요**, 기존 `/api/leads`와 동일한 모양 |
| C | `/check` 페이지를 `app.trops.kr`에 신설 | 랜딩에서 도메인이 튀고, 「로그인 없이 바로」와 앱 도메인이 충돌 |

B는 홉이 하나 늘지만, **fail-open 원칙(§9) 덕에 지연이 사용자 화면에 나타나지 않습니다.** 전달 실패도 화면을 막지 않습니다.

**요청** (브라우저 → `trops.kr/api/prestep`)
```
{
  "sessionKey": "<uuid>",          // 필수
  "situation": "docs_received",    // 선택
  "docs": ["nda"],                 // 선택
  "experience": "first",           // 선택
  "completedStep": 2,              // 필수
  "exitedVia": null,               // 선택
  "ctaClicked": null,              // 선택
  "referrer": "<document.referrer>" // 최초 1회만
}
```

**응답** `{ "ok": true }`

**동작**
- `sessionKey`로 **upsert**. 같은 키 재호출은 갱신(멱등)
- `completedStep`은 **더 큰 값만 반영**(뒤로가기로 되돌아가도 최대 진행도가 남게)
- 서버가 값 검증: enum 밖의 값은 해당 필드만 버리고 나머지는 저장. **400을 던지지 않음**
- 응답에 데이터를 담지 않음 — 화면은 서버 응답을 기다리지 않음(§9)

### 4-3. 이탈 신호 확보

`beforeunload`에 마지막 저장을 걸지 **않습니다**(모바일에서 신뢰도가 낮음). 대신 **문항별 저장으로 `completed_step`이 이미 남아 있으므로**, 이탈은 "마지막 저장 이후 완료 기록이 없음"으로 사후 판별합니다. 추가 코드 0.

`exited_via`는 명시적 행동만 기록: `skip`(건너뛰기 클릭) · `bypass_link`(바로 비교해 보기 클릭) · `completed`(결과 화면 도달). `abandon`은 **저장하지 않고 집계에서 파생**합니다.

## §6 프리필 전달 — `/precheck` 연결

기존 `?intake=ok&r=token` 선례를 그대로 따릅니다.

```
/precheck?pre=<session_key>&docs=nda,quote_pi
```

| | |
|---|---|
| `pre` | `session_key`. `/precheck` 제출 시 함께 보내 `intake_id` 역기입에 사용 |
| `docs` | 문서유형 프리필용. **쿼리에 직접 실어** 서버 조회 없이 즉시 렌더 |
| 매핑 | `service_license`·`other_doc` → 폼 「기타」로 접힘(다대일). `none`은 파라미터 자체를 붙이지 않음 |
| URL 정리 | 프리필 적용 후 `history.replaceState`로 파라미터 제거 — 기존 코드와 동일 방식 |

🔴 **M-2 해소 — 필드명을 알아내지 않고, 알 필요가 없게 만듭니다.**

기존 입력의 `name`·`value`를 그대로 두고, **`data-doctype` 속성만 추가**합니다.
프리필 코드는 `[data-doctype="..."]`로만 찾습니다.

🔧 **정정 (2026-08-15).** 이 절은 원래 프리필 대상을 「기존 **체크박스 4개**에
`data-doctype` 4개 추가」로 적었습니다. **실물은 체크박스가 아니라 단일선택
`<select>`입니다.** 아래는 `precheck.html`을 실제로 열어 확인한 현재 상태입니다.

```html
<!-- precheck.html — <select id="intake-doc-type" name="docType" required> -->
<option value="nda"       data-doctype="nda"            selected>비밀유지계약서(NDA) — 현재 지원</option>
<option value="contract"  data-doctype="sales_contract" disabled>거래계약서 — 준비중</option>
<option value="quotation" data-doctype="quote_pi"       disabled>견적서 — 준비중</option>
<option value="po"                                      disabled>발주서(PO) — 준비중</option>
```

| 실물 | |
|---|---|
| 형태 | 복수선택 체크박스가 아니라 **`<select>` 단일선택**. 보기 4개 |
| `data-doctype` | **3개**만 붙어 있음 — `nda`·`sales_contract`·`quote_pi` |
| 「기타」 보기 | **없음.** 사전 확인의 `other`를 받을 자리가 없습니다. 발주서(PO)에 임의 배정하지 않은 것은 의도입니다 — 그것이 설계서 §7이 금지한 「모르는 것을 아는 척 배정하기」입니다 |
| 고를 수 있는 보기 | **`nda` 하나뿐.** 나머지 셋은 `disabled`이고, 서버(`parseDocType`)·DB(`intake_doc_type_allowed`)가 `nda` 외를 400/거절로 막습니다 |

**그래서 프리필의 실제 동작**은 이렇습니다.

| 넘어온 값 | 결과 |
|---|---|
| `nda` | 선택됨 |
| `sales_contract`·`quote_pi` | `<option>`은 있으나 `disabled`라 **건너뜀** |
| `service_license`·`other_doc` | `check.html`이 `other`로 접어 보내는데 받을 `<option>`이 없어 **아무 것도 안 함** |
| 복수 값 | **성립하지 않음.** 단일선택이므로 **고를 수 있는 첫 값 하나만** 반영 |

어느 경우든 기본값 `nda`가 그대로 남으므로 화면이 깨지거나 잘못된 값이
저장되지 않습니다. 뒤집어 말하면 **오늘 이 프리필이 실제로 바꾸는 값은
없습니다** — 유일하게 고를 수 있는 보기가 기본값과 같기 때문입니다. 이 연결은
「기타」 보기가 생기거나 준비중 보기가 열리는 날을 위해 미리 깔아둔 배선이고,
그날 그 `<option>`에 `data-doctype` 한 칸을 붙이면 저절로 이어집니다.

| 근거 | |
|---|---|
| 1 | **폼 제출 로직이 무변경.** `name`·`value`를 안 건드리므로 기존 접수 처리·메일·결제 흐름에 영향 0 |
| 2 | ~~**실측 대기가 사라짐** — precheck.html을 열어보기 전에 작업 8을 설계할 수 있고, 구현자는 속성 4개만 붙이면 됨~~ 🔧 **이 근거가 위 오류의 원인입니다.** `precheck.html`을 열어보지 않고 설계한 결과가 「체크박스 4개」였습니다. `data-doctype`으로 찾는 방식 자체는 실물에서도 그대로 살아남았지만, **속성을 붙일 자리의 형태를 틀리게 적었습니다.** 다음 사람은 연결 방식은 파일을 안 열고 정해도, **붙일 대상의 태그 종류와 보기 개수만은 반드시 실물로 확인**하십시오 |
| 3 | **나중에 폼이 바뀌어도 안 깨짐.** `name`이 리팩터링돼도 `data-doctype`은 의미 기준이라 그대로 |
| 4 | 라벨 텍스트로 찾는 방식은 문구가 바뀌면 조용히 깨지므로 채택하지 않음 |

`check.html`이 `service_license`·`other_doc`을 `other` 한 값으로 접어 보내는
다대일 매핑은 그대로입니다. 다만 **받는 쪽에 `other` 보기가 없어** 현재는 그
값이 도착해도 아무 일도 일어나지 않습니다(위 표).

## §10-2 운영자 화면 — `app.trops.kr/admin/` ✅ 대표 결정

데이터를 운영자가 볼 자리를 `trops_a`의 기존 관리자 영역 밑에 둡니다. 계정은 `contact@theo-ne.com`.

### 이 결정이 부수적으로 해결하는 것

**저장소 불확실성이 사라집니다.** main_web에 DB가 있는지 확인이 안 됐는데(§0), 화면을 `trops_a`에 두기로 하면 저장소도 자연히 그쪽으로 정해집니다. `trops_a`에는 대조 실행·검수 기록이 이미 쌓이므로 DB 존재가 확실합니다.

### 화면 사양 — 초기엔 목록 하나로 충분

**`/admin/prestep-sessions`**

경로명 근거 4:

1. 기존 `admin/nda-runs`와 **같은 꼴** — kebab-case + 복수 명사, 2단어
2. 테이블 `intake_prestep_sessions`·API `/api/prestep`과 **어휘 일치** → 코드에서 `prestep` 한 단어로 추적됨

4. 고객 노출이 0인 운영자 URL이라 「진단」 금지 등 **명칭 규칙 적용 대상이 아님** — 코드 식별자가 이미 `prestep`으로 굳었으므로 URL도 그대로
