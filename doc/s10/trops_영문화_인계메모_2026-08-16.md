### 만든 방법 — 손으로 다시 쓰지 않았습니다

국문 원본을 읽어 **문구만 치환**하는 스크립트로 뽑았습니다. 스크립트는
`/private/tmp/.../scratchpad/build-en*.js` 에 있고 세션 임시 파일이라 남지 않습니다.
남는 것은 **결과물과 그 결과물을 지키는 테스트**입니다.

이유: 손으로 옮기면 CSS 한 줄·id 하나가 조용히 어긋나고, 그 어긋남은 국문을 고칠 때가
되어서야 발견됩니다. 치환은 개수까지 단정하고(예상보다 많거나 적으면 실패), 마지막에
「주석을 걷은 뒤 한글이 남았는가」로 미번역을 잡았습니다.

## 2. 구조 규칙 — 「국문 그대로 영문화」

**id 순서가 네 쌍 모두 한 칸도 어긋나지 않습니다.** CSS·클래스·섹션 순서도 같습니다.
국문을 고칠 때 영문에서 **같은 자리**만 찾으면 됩니다.

의도된 차이는 세 곳뿐이고, `test/naming-consistency.test.js` 의 `STRUCT_DELTA` 에
**개수로** 적혀 있습니다 — 새 차이를 만들면 그 숫자부터 고쳐야 하고, 그 순간 사유를
적게 됩니다.

| 파일 | 차이 | 사유 |
|---|---|---|
| `en.html` | `<p class="hero-lead">` +1, `<span class="cta-row-note">` +1 | 카피 초안 히어로가 국문보다 한 문장 깁니다(「For now, you can start with document comparison.」). 05 근거 CTA 앞의 「If you have a document, check it now.」도 초안 원문입니다. 새 클래스를 만들지 않고 이미 있는 것을 한 번 더 썼습니다. |
| `en-precheck.html` | `.lang-notice` −1 | 「이 폼은 한국어 전용」 안내. **이 페이지가 그 영문판**이라 안내할 대상이 없습니다. CSS 규칙은 1:1 로 두려고 남겼습니다. |
| `en-refund.html` | 푸터 링크 +1, 법적 고지 `<p>` +1 | 아래 §5 참조 — 국문 `refund.html` 푸터가 나머지 국문 4개와 어긋나 있습니다. |

`<br>` 은 구조 비교에서 **뺐습니다**. 줄바꿈 자리는 언어마다 달라야 하기 때문입니다 —
국문 기준으로 잡힌 `max-width`(ch 단위)에 영문을 그대로 넣으면 1440px 에서 마지막 줄이
낱말 하나짜리 고아가 됩니다. 영문 `<br>` 자리는 **실측으로 다시 잡았고**, 문구는 한
글자도 바뀌지 않았습니다(마크업만 바꾼 것이라 정본 §2-3 이 허용).
⚠️ 문구나 폭을 고치실 때 함께 재십시오.

## 3. 배선 — 영문 경로가 끝까지 영문입니다

랜딩 주 CTA 2곳(히어로·결) → `/en-check` → `/en-precheck` 〔구조결정 A안〕.

옛 `en.html` 은 `/precheck?lang=en` 으로 **국문 접수 폼**에 곧장 보냈고, 도착지에서
「이 폼은 한국어 전용」 안내를 만나는 흐름이었습니다. 지금은 `?lang=en` 이 영문
페이지에서 사라졌습니다.

`en-precheck.html` 에서 국문으로 새던 자리 **셋을 실측으로 찾아 고쳤습니다** —
마크업의 `href` 만 봐서는 안 걸리는 것들입니다:

- `history.replaceState(…, '/precheck')` — 프리필 뒤 주소창 정리. 그대로 두면
  새로고침 시 **국문 접수 폼**이 열립니다.
- 토스 `successUrl` / `failUrl` — 결제 복귀. 그대로 두면 영문에서 결제한 사람이
  국문 승인 확인 화면을 만납니다.

`test/naming-consistency.test.js` 「영문 경로가 끝까지 영문이다」가 이 셋을 못질합니다.

### 접수 폼 계약은 언어와 무관합니다

`name=` · `value=` · `data-doctype` · `preSessionKey` · `<option>` 의
`selected`/`disabled` · 결제 로직이 국문과 **글자 그대로** 같습니다(테스트가 확인).
가격(₩300,000)도 국문과 **정확히 같은 자리**(`.pay-area` 안 · 유료 경로를 고른 뒤)에만
있습니다.

## 6. 🔴 발견 사항 — 과금 게이트 사본이 정본과 어긋났습니다 (영문화와 무관)

`npm test` 의 `precheck-charge-gate.test.js` 「법 게이트가 정본과 같다」가 **작업 전부터**
실패하고 있었습니다.

```
this repo  api/_precheck-charge-gate.js   LAWYER_CONFIRMATION = { S62_44: false, S62_03: false }
trops_a    lib/payment/precheck-paid-gate.ts  LAWYER_CONFIRMATION = { S62_44: true,  S62_03: true }
```

정본(trops_a)에서 두 항목이 **열렸는데** 이 저장소 사본이 닫힌 채입니다. 즉 유상 개시가
이 저장소에서만 막혀 있습니다.

⛔ 이 값을 손으로 맞추지 않았습니다. 테스트 주석이 정한 순서가
**① 원장 → ② trops_a 정본 → ③ 이 사본** 이고, 값을 뒤집는 것은 유상 과금을 여는
결정이라 코드 정리의 몫이 아닙니다. 원장(PRD-62 §7 · S62-44 · S62-03)을 확인한 뒤
반영해 주십시오.

## 8. 2026-08-17 후속

### 8-1. 푸터 태그라인 통일 · 검사 범위 확대

값이 셋으로 갈라져 있었습니다 — `수출 사전점검 · 바이어 확인 · 기한 관리`(index·check·
precheck) / `수출 거래 운영`(refund·nda·uae) / `수출 사전점검`(privacy) / `Export
pre-check`(en-privacy). 다섯 곳을 확정값으로 맞췄습니다.

원인은 **검사가 index·precheck 둘만 보고 있던 것**입니다. 두 곳만 보는 검사는 두 곳만
지킵니다. 이제 목록을 손으로 적지 않고 `scripts/build-static.js` 의 `STATIC.html` 에서
읽습니다 — 페이지를 새로 만들면 다음 실행부터 저절로 검사 대상이 됩니다. 그러려고
`build-static.js` 에 `require.main === module` 가드와 export 를 넣었습니다.

⚠️ **손대지 않은 것**(성격이 다릅니다):
- 법적 고지가 3줄(index·check)과 2줄(나머지 5) 두 형태입니다. 둘 다 「법률 자문이
  아니다」를 말하고 긴 쪽이 더 넓게 방어합니다. 명칭 문제가 아니라 **법적 문면 선택**
  이라 임의로 통일하지 않았습니다.
- 푸터 링크의 self 링크 유무와 [TROPS 홈] 유무가 페이지마다 다릅니다. 지금 깨지는
  것이 없습니다.

`en-refund` 는 국문과 1:1 로 되돌렸습니다 — 어제 국문 푸터가 통째로 드리프트했다고 본
판단이 틀렸기 때문입니다. **이제 네 쌍 모두 구조가 완전히 같습니다**(`STRUCT_DELTA`
`en-refund` = `[0, 0]`).

### 8-2. 영문으로 접수하면 그 뒤도 영문으로 갑니다

🔴 **폼에 칸을 더하지 않았습니다.** 두 페이지는 구조가 1:1 이라 한쪽에만 칸을 더하면
그 자리에서 갈라집니다. `<html lang>` 이 이미 다르므로 **같은 코드**가 그것을 읽어 서로
다른 값을 보냅니다.

🔴 **언어는 접수 성립의 조건이 아닙니다.** 모르는 값은 400 이 아니라 국문으로 떨어집니다.

영문으로 나가는 것: 접수 확인메일 · 자료 전달 메일 · 삭제 확인 메일 · 서류 종류 표기 ·
범위 밖 안내(routeNotice). **운영자 메일은 언제나 국문**입니다 — 읽는 사람이 한 명이고
언어가 안 바뀝니다. 영문으로 갈아 끼우면 받은편지함에 두 언어가 섞여 검수가 느려집니다.

⚠️ 조회는 **붙여서 한 번, 없으면 떼고 한 번** 합니다. 그냥 붙였으면 컬럼이 없는 DB 에서
**전달이 멈추고**(`delivered_at` 이 환불 기산점) **삭제가 막혔을** 것입니다.

⚠️ 환불·결제 리마인더 메일은 영문화하지 않았습니다 — 유료 경로가 과금 게이트로 닫혀 있어
(`api/intake.js:197` `rejectIfChargeBlocked`) **발화 자체가 불가능**합니다. 게이트를 여는
날 §6 과 함께 보십시오.

### 8-3. 영문 문구에서 em dash(—)를 걷었습니다

국문의 「—」 자리를 그대로 따라가 문장마다 붙어 있었고, 영문에서는 그 빈도가 기계가 쓴
문장처럼 읽힙니다. 글자만 빼지 않고 자리마다 다시 썼습니다(문장 안 삽입 → 마침표·쉼표 /
타이틀·옵션 구분 → `·` / 기관명 동격 → 쉼표 / 대체 텍스트 → 콜론 / 인용 출처 → 제거).
en dash(`–`)는 숫자 범위(`3–5 business days`)에 옳은 표기라 남겼습니다.

문장이 짧아지며 `<br>` 자리가 어긋나 히어로·스토리·인용문 3곳을 1440px 실측으로 다시
잡았습니다. `naming-consistency` 가 영문 5개 페이지와 고객용 영문 메일에서 em dash 0건을
셉니다.

### 8-4. DB 마이그레이션 0-K — 적용 완료

기존 17건의 값     전부 'ko' · null 0건  → not null default 'ko' 적용됨

없어도 동작에는 지장이 없습니다 — `parseLocale` 이 이미 아는 값만 통과시키고, 이 제약은
