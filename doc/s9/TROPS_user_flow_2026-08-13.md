# TROPS 랜딩/가격/구조 통합 흐름 (2026-08-13)

## 0. 핵심 원칙

1. 계정(로그인)은 모든 상품의 공통 열쇠 — 사전점검, 기한관리, 바이어확인이 같은 계정 안에서 동작 (HS코드는 별도 계정접근이 필요한 기능이 아니라 사전점검 리포트 본문에 포함된 콘텐츠)
2. 결제는 AI 실행 전, 사전점검이라는 개별 상품에만 걸림 — 비용 노출 없음, 기한관리는 무료로 별도 열림
3. "결과 전달 전 전액환불" 정책이 선결제 마찰을 상쇄
   - 요청형: 고객이 결과 받기 전 스스로 취소 요청 → 정책대로 전액환불
   - 자동형: 검수 실패로 결과 생성이 불가할 경우 → 고객 요청 없이 시스템이 자동 환불
4. 랜딩 셀프서브(이미 의문 있는 고객)와 인터뷰 채널(대표가 의문을 만들어주는 능동적 영업)은 같은 상품으로 수렴 — 서로 다른 카피가 필요 없음

## 1. 상품/채널 구조

```
"첫 수출이라 무엇부터 봐야 할지 모르겠다면" (랜딩 진입 문구, 유지)

        ├─ "지금 급한 건 이거다" → 수출 사전점검 (셀프서브, 현재는 NDA만 지원)
        └─ "전체를 봐줬으면 좋겠다" → 상담신청 → 인터뷰 채널(재무진단 후 모듈 맞춤구성)

+ 기한관리: 사전점검 결제 여부와 무관하게 완전 공개 무료 (결제자는 이미 로그인 상태라 진입만 더 빠를 뿐, 전용 혜택 아님)
+ 바이어확인: 사전점검 결제자 전용 보너스 (독립 실행, 별도 언락)
+ HS코드: 별도 보너스 아님 — 사전점검 리포트 본문에 이미 포함된 콘텐츠
```

- 상위 카테고리명은 "수출 사전점검"으로 통일. NDA는 현재 지원하는 첫 서류 종류일 뿐 — 계약서·견적서 등 확장 예정이므로 CTA/버튼에 "NDA"를 박아넣지 않음. 접수 화면 안에서만 "현재는 NDA만 지원"으로 범위 명시.
  - **이 원칙의 진짜 이유(단순 확장성 아님):** 현장 피드백에 따르면 홈페이지 타이틀·헤드라인에 "NDA"가 노출되는 순간 "기밀서류를 대놓고 요구하는 곳"이라는 방어기제가 작동해 자료제출 자체를 막음. 그래서 이 원칙은 **CTA 버튼뿐 아니라 페이지 `<title>`/메타description/og:title/헤드라인·서브헤드라인 전체**에 적용해야 함 — "NDA"라는 단어는 접수화면 안에서, 이미 신뢰관계가 형성된 단계에서만 등장.
- 인터뷰 채널은 대표가 먼저 리스크를 짚어 의문을 만들어내는 능동적 영업이며, 랜딩 셀프서브와 최종 상품(사전점검)이 동일하므로 카피 이원화 불필요.

### 인터뷰 진행 원칙 (현장 피드백 반영)

- **직접 자료요청 금지, 경험담 선행**: NDA·재무제표를 "보여주세요"로 시작하지 않음. 비밀누출 우려·무지 노출에 대한 창피함 때문에 직접 요청하면 방어기제가 작동해 자료가 안 나옴. 대표님의 과거 사례("예전에 이런 일이 있었는데 이런 문제가 있더라")를 먼저 공유 → 상대가 스스로 "우리 것도 봐달라"고 역요청하게 만드는 방식으로 유도.
- **목표는 자각, 진단 선언이 아님**: "여기가 문제네요"를 우리가 먼저 말하지 않고, 질문·사례로 유도해서 고객 스스로 문제를 자각하게 함.
- **재무상황 파악이 전체 전략의 전제**: 재무제표를 미리 파악해야 그 회사에 맞는 가격·상품을 조정할 수 있음 — 인터뷰 패키지의 완전 가변가 원칙이 성립하려면 이 재무 파악이 선행돼야 함.
- **고정 번들 아닌 모듈 맞춤구성**: "리포트+교육1시간"류 고정 패키지("올인원") 대신, 재무진단 후 회사 상황에 맞춰 필요한 모듈(진단리포트/교육1시간/바이어확인 우선처리/기한관리 온보딩 지원 등)을 그때 조합. 재무파악이 가격뿐 아니라 상품구성에도 반영돼야 "원하는 가격·원하는 상품"이라는 원칙이 완결됨 — 가격만 유동적이고 구성이 고정이면 절반만 반영한 것.
- **무지 안전장치 문구**: "모르시는 게 당연합니다"를 인터뷰 오프닝 표준 문구로 사용. 랜딩 헤드라인의 "무엇부터 봐야 할지 모르겠다면" 톤과도 일치시킴.
- **"NDA" 직접 언급도 인터뷰 초반에는 지양**: 오프닝은 "수출 사전점검"/경험담 프레이밍으로 시작하고, 실제 서류 종류(NDA)는 신뢰관계 형성 후에 구체화.

### 랜딩 심리설계 (인터뷰 기법을 셀프서브 채널로 확장)

인터뷰에서 쓰는 "직접요청 대신 경험담 선행, 자각 유도" 기법을 랜딩 자체에도 적용:

- **경험담 좌우비교 섹션 신설**: 좌측 "많은 대표님이 처음엔 이렇게 생각하셨습니다"(막연한 안심: "표준 양식이겠지") vs 우측 실제 사례(구체적 조항 문제 예시). 직접 "당신 계약도 위험하다"고 말하지 않고, 사례 나열 후 질문 하나("이 조항, 본 적 있으신가요?")로 마무리 — 스스로 확인하고 싶게 만듦.
- **무지 노출 창피함 대응 섹션**: "모르시는 게 당연합니다"를 일반 안심 문구 하나로 두지 않고, 익명화된 사례 나열 형태로("이런 것도 처음엔 다들 모르셨습니다") — 구체적 사례가 광고성 안심 문구보다 신뢰도 높음.

### 재무 리스크 프레임 (헤드라인 유지 + 서브헤드라인 보강)

리서치 결과, 정확한 %로 추산된 피해통계는 확인 안 됨. 대신 한국무역보험공사가 명시한 구조적 사실을 카피 근거로 사용 가능: **"거래처 한두 곳에 매출이 집중된 수출 초기 기업은, 대금 미회수 단 한 번으로 자금난에 빠질 수 있다."** 첫 수출기업 대부분이 거래처 1~2곳뿐이라 거의 모든 방문자에게 해당되는 문장.

- **"첫 수출"은 데이터로 검증된 진입 키워드이므로 헤드라인은 교체하지 않고 그대로 유지.** 헤드라인은 유입을 담당(그대로 "첫 수출이라 무엇부터 봐야 할지 모르겠다면"), **서브헤드라인/바로 아래 줄에서 재무리스크 문장으로 보강**해 전환을 담당 — 예: "거래처 한두 곳에 매출이 몰린 지금, 이 거래 하나가 회사 전체에 걸려있을 수 있습니다."
- 헤드라인 교체가 아니라 헤드라인+서브헤드라인 조합으로 처리 — 검증된 유입 경로를 흔들지 않으면서 "무지"를 "재무리스크"로 구체화.

### 기한관리 미리보기 — 심리적 훅 + 로그인 정책 확정 (2026-08-13 코드조사 반영)

지금 "미리보기"는 기능설명적이라 훅이 약함. NDA쪽 훅이 "비밀누출 걱정"이라면, 기한관리쪽은 **"내가 뭘 놓치고 있는지도 모른다"는 통제감 상실 공포**가 맞는 지점. "계약서 하나에 기한이 몇 개나 숨어있는지 아세요?"처럼, 놓치고 있을 수 있는 것의 존재/개수를 질문으로 먼저 던지는 방식으로 카피 재설계.

**로그인 정책 충돌과 해결**: 기존 접수흐름은 "로그인 불요"가 의도적 설계원칙(주석에 명시)인데, 이 md의 원칙0-1은 "계정이 모든 상품의 공통 열쇠"로 반대 방향. **결론: 접수/사전점검 자체의 로그인 정책은 그대로 유지(변경 안 함)** — 기존 결정을 뒤집을 근거 부족. 기한관리 미리보기는 별도로 아래처럼 해결:

- **랜딩 아코디언 안**: 실제 대시보드 스크린샷(마스킹된 지도) 이미지 사용 — 개발부담 없음
- **"기한관리 미리보기" 클릭 → app.trops.kr 진입**: 코드조사로 확인된 기존 `AnonymousHomePreview`(app/page.tsx:264-289, 로그인 없이 접근 가능하나 현재 DB 조회 0건이라 빈 상태)를 그대로 재사용하고 **예시데이터(프랑스1/아랍에미리트1 등 마스킹 샘플)로 시딩**. 신규 개발 아니라 기존 컴포넌트에 샘플 데이터만 채우는 작업.
- `/procedures` 이하(실사용 데이터 다루는 곳)는 기존 로그인 하드게이트 그대로 유지 — 건드리지 않음.
- 이 방식으로 "로그인 없이 실제 화면을 보여주고 싶다"는 목표와 "초기엔 로그인 장벽이 이탈을 만든다"는 우려를 최소 개발비용으로 동시 해결.

**FTA 세율조회는 이 4층구조에서 제거 — 랜딩의 독립 섹션이 아니라 결제 후 사전 점검 리포트 콘텐츠 후보 (4-1장 참고). 감정선(기-승-전-결)이 신뢰증명 다음 곧바로 행동(결)로 이어지도록 무관한 기능섹션을 감정선 사이에 두지 않음.**

- **색 토큰 확정**: 주 액센트는 `#1D4ED8`(블루)로 확정 — 이전 메모리에 남아있던 "틸 호버 액센트"는 2026-08-11 시각사양서로 대체됨. 초록·주황은 "판정신호로 읽히기 때문"에 도입하지 않음 — §109 "판단하지 않는다" 원칙이 색상 레벨까지 적용된 것.

## 4. 가격 — ₩300,000을 "1차 테스트가"로 확정 (완전 미정에서 전환)

### 핵심 기능 (기능으로 재포장)

### 핵심 기능 3분류 (랜딩 대표 노출용, 확정)

**층위 정리**: 사전점검·바이어확인·기한관리는 각자 독립된 CTA/흐름/화면을 가진 완결된 상품이고, HS코드·FTA조회는 그 안(사전점검 사전 점검 리포트)의 세부 콘텐츠 항목 — 서로 다른 층위라 3분류에 함께 놓지 않음.

```
1. 문서 대조 (사전점검, NDA 등)  — 거래 시작 전
2. 바이어 확인 (추후 역제안)      — 거래 시작 전
3. 기한 관리                      — 거래 시작 후
```

기존 랜딩 태그라인 "거래를 시작하기 전에 한 번, 시작한 후에 한 번"이 이미 이 구조(전 2개 + 후 1개)를 말하고 있었음 — 두 개의 별개 상품이 아니라 **거래 하나의 전체 생애주기를 확인해주는 하나의 완결된 서사**로 재해석. HS코드/FTA조회는 이 3분류와 별개로 사전점검 사전 점검 리포트 내 세부 콘텐츠로 위치.

### 마케팅 카피 방향 — ⚠️ 법적 안전마진을 낮추는 선택 (의도적 결정)
- USP 전면 카피: "NDA 검토 시간 단축", "17개 항목 자동 대조", "표준 조항과 다른 부분만 바로 확인", "확인 기록 자동 보관"
- **"판단하지 않습니다" 표현은 랜딩 전면 카피에서 제거, FAQ와 약관/백엔드에만 유지.** 원래 이 문구는 §109 케이스법 기반 Gray Area 방어 전략의 핵심 신호였음(R1-R9 룰셋). 매출 우선순위로 전면 노출을 줄이는 이번 결정은 **법적 안전마진을 낮추는 트레이드오프**이며, 대표(변호사)가 이를 인지하고 선택한 것으로 기록.
- 확인 기록 로그도 "분쟁/보험청구 시 증거자료로 활용 가능"류 표현은 **내부 기능스펙에서는 명확히 유지**하되, **공개 카피(랜딩·제품화면)에는 "확인 시점을 기록해 둡니다" 수준으로 완화**. 법적효력을 직접 주장하는 문장은 정식 법률검토 통과 전까지 대외 노출 안 함.

### 전문가 확인 유도 — 백엔드 유형별 태깅, 사용자 노출은 종합 1회

- **백엔드**: 리스크 유형별 태그는 시스템 내부(분석·통계용)로 유지 — 어떤 유형이 몇 건 나오는지 데이터 축적
- **사용자 노출**: 대조 진행 중 항목별로 "전문가 확인 필요" 플래그를 띄우지 않음 (평가행위로 보일 소지 있어 제외). 대신 **대조 완료 후 결과 화면 맨 아래에 종합 안내 1개**: "전체적으로 전문가 확인을 원하시면" → 제휴 변호사/관세사 무료 연결
- 확인 기록 로그가 여기서도 이어짐: 전문가 연결 여부·연결 후 조치까지 기록 → "판단은 전문가가, 기록은 TROPS가"로 역할 분리
- **무료/유료는 보류 — 클릭률 데이터로 결정.** 이 종합CTA의 클릭률 자체가 H2(판단 vs 비교자료로 충분) 검증 대체 수단 — 인터뷰 없이 실제 행동데이터로 확인 가능. 리드는 초기 단계엔 대표님이 직접 수신.

### 바이어 역제안 — 조건부 파일럿 (스코프 재확장, 게이팅 유지)
- 방식: 고객이 등록한 바이어 정보를 공개정보 기준으로 검증만 하고, 알선/매칭은 안 함
- "역제안"은 TROPS가 직접 하지 않고 제휴 KOTRA 네트워크(이석현, 황충연 등)로 리드 전달
- 실행 조건(둘 다 통과 전 개발 안 함): ① 법적검토(무역대리업/전자상거래법 저촉여부) ② 인터뷰에서 반응 확인
- 리소스: 별도 스프린트, NDA엔진/main_web_page 완성 이후 착수

### 전문가 리퍼럴 — 무료 리드전달 (기능 먼저, 가격화는 보류)
- flat fee 폐기 → 완전 무료 리드전달 (TROPS는 수수료 안 받음, §34 리스크 회피)
- 전문가 유인: 검증된 리드 확보
- **가격화(추후 유료 전환 여부)는 지금 정하지 않고 기능만 먼저 구축**
- 바이어 역제안도 같은 원칙 — KOTRA로 무료 리드 전달, 알선업 등록 이슈 회피

### 랜딩 노출 범위
- 바이어 검증 기능은 파일럿 단계 — 랜딩 전면 노출 안 함, 베타/얼리액세스로 소수 공개

## 5-1. 검토 과정에서 추가된 보완 기능

1. **검수 SLA 명시** — 결제 화면에 "영업일 기준 O시간 내 전달" 표기. 선결제 구조에서는 환불정책보다 "언제 받는지"가 더 큰 불안 요소일 수 있음.
2. **검수 실패 분기** — 운영자 검수에서 품질 미달/AI 오류 판단 시 **즉시 자동 환불 + 고객 안내 메일**. 재실행 단계를 두지 않는 것이 확정 방식입니다(위 3장 흐름도와 같음). 지금까지 흐름엔 검수를 "통과 전제"로만 그려져 있었음.
3. **대기 공백 동안 기한관리 노출** — 결제확인 메일에 기한관리 미리보기 링크 포함. 검수 대기 시간 동안 고객이 아무 접점도 없는 공백을 제품 노출 기회로 전환.
4. **사전점검-기한관리 데이터 자동 연동** — 기한관리 등록 시 사전점검에서 입력한 목적국/거래정보를 재입력 없이 끌어와 마찰 감소, 두 상품이 "같은 데이터의 연속"이라는 인식 형성.
5. **저마찰 이의제기 경로** — 결과에 의문이 있을 때 환불/상담신청 외에 "이 항목 다시 봐주세요" 경로 제공. 환불로 새는 것을 막고 검수 품질 개선 루프 확보.
6. **결제 미완료 리마인드** — 접수 후 결제 안 한 고객에게 N시간 후 1회 발송. 이미 파일 업로드까지 한 고성의도 이탈자 회수.
7. **재구매 시 접수 폼 단축** — 이메일 매칭 시 이전 접수 정보 자동 참조, 파일 업로드만. (접수 폼에는 로그인/계정이 없습니다 — 위 3장과 같음.)
8. **결과화면 반복구매 CTA** — "다른 바이어 NDA도 확인" 버튼으로 재구매 경로 노출.
9. **카카오 알림톡 채널** — 타겟(한국 중소기업 대표)에게 이메일보다 카카오톡 확인이 빠르고 확실함. 결제확인/결과전달/기한알림(D-7·D-1) 발송에 알림톡 옵션 추가. 국내 표준 API, 저비용/고효과.
10. **결제~전달 사이 진행상태 표시** — "접수됨 → 검토중 → 전달완료" 단순 상태 라벨. 검수 대기 공백 동안 불안감 완화. 텍스트 라벨 추가 수준, 거의 무비용.
11. **결과 웹뷰 "동료에게 공유" 버튼** — 결제자가 실무자에게 리포트를 넘기는 경우가 실제로 있을 수 있음. 링크 공유 버튼 하나로 조직 내부 전파 유도, 거의 무비용.
12. **기존 신뢰섹션("무엇을 근거로 비교하는지", OGL 라이선스 출처 명시) 보존 명시** — 이번 개편 작업 중 실수로 삭제되지 않도록 "유지" 항목으로 별도 기록.
13. **FAQ 문구 구체화** — "셀프서브 사전점검이랑 상담신청은 뭐가 달라요?" → "지금 바로 결과를 받고 싶으시면 사전점검, 저희 대표님과 먼저 상황을 얘기하고 싶으시면 상담신청입니다." 채널분기 혼동 보완용 FAQ가 지금까지 "필요하다"는 언급만 있었고 실제 문구가 없어 작성 시 누락 위험 — 지금 명문화.
14. **환불고객 피드백 후속 컨택** — 환불(요청형/자동형 모두) 발생 시 사유를 짧게 묻는 후속 연락. 별도 필드+수동 컨택 수준으로 저비용이나, 지금 단계(가격·상품 검증 초기)에는 이 데이터가 매우 값짐.
15. **데이터 삭제정책 FAQ 보존 명시** — 기존 라이브 FAQ "원본은 30일 뒤 자동삭제, 요청 시 즉시삭제"도 신뢰신호이나 md에 보존 언급이 없었음. 12번(근거출처 보존)과 함께 개편 시 누락 방지용으로 기록.

### 6-1. main_web_page — 트랙A(색토큰/버튼/타이포/섹션) 이미 완료

- 실제 섹션은 10개 정본 리듬(헤더→히어로→안심문구→2층카드→HOW→신뢰→로드맵→FAQ→마감CTA→사전등록폼→기관안내→푸터)을 이미 따르고 있음 — **이 md의 "4층구조" 스케치는 참고용이었을 뿐, 실제 구현 시엔 이 10개 정본 리듬 안에 신규 블록을 끼워넣어야 함**

### 6-2. main_web_page — 아직 없는 것 (실제 구현 필요)

- 경험담 좌우비교 / "모르시는 게 당연합니다" / 핵심기능 3분류 아코디언 — **3개 모두 0건**

- **"상담 신청" CTA는 과거 "유상자문 오인" 이유로 이미 제거된 이력** — "문의하기"로 명칭 확정하여 재도입 (위 1장 반영됨)

### 6-3. trops_a — DB저장버그 해소, 검수완료 자동발송 이미 구현됨

- **DB저장버그: 완전 해소(2026-08-13 당일 수정).** 진짜 원인은 RLS나 응답판정 로직이 아니라 `PRECHECK_SUPABASE_URL`이 `http://`로 설정돼 PostgREST의 301 리다이렉트가 POST를 GET으로 깎아먹은 것. `normalizeSupabaseUrl`로 https 강제 승격하여 해결.
- **검수완료(markReviewed) → 자동 메일발송: 이미 완료.** `scripts/deliver.js` 수동실행 불필요해짐 — 검수완료 클릭 시 서버 액션 내에서 자동 발송(best-effort).
- 단, 지금까지 실행된 run 2건 모두 파이프라인 자체 실패(llm_error/parse_error) — **성공 케이스의 검수→발송 전 과정이 아직 실측 안 됨**

### 6-4. trops_a — 핵심 미해결: 매직링크 미연결 (최우선)

- 이메일로 오는 매직링크(`?r=<token>`)는 여전히 main_web_page 자체의 단순 접수확인 화면만 보여줌 — **trops_a `/c/[token]` 결과지로 전혀 이어지지 않음**
- 현재 `/c/[token]`으로 가는 유일한 경로는 결제 완료 직후 같은 브라우저 세션에서 발생하는 JS 리다이렉트(`intakeId` 사용, 매직링크의 `access_token`과는 다른 식별자)뿐
- **영향**: 무상 접수 고객 + 메일함으로 나중에 재방문하는 모든 유상고객이 결과지에 도달할 방법이 없음. C-03 리다이렉트 시점도 "검수완료 시점"으로 옮기려던 계획이 아직 미실행 — 여전히 "결제 확정 즉시"(검수 전) 리다이렉트라 검수게이트로 인해 "결과확인중" 화면만 보임
- **접수 폼 로그인 정책**: "회원가입 불요"가 기존 의도적 설계원칙 — 이 md의 계정중심 원칙과 충돌, 위 1장에서 유지 결정함

### 6-5. trops_a — 그 외 갭

- 결과화면(`/c/[token]`) 하단카드: 바이어확인/기한관리 카드 0건. 단 "상품관세조건확인"/"상대방법인등록확인" 자리표시자 버튼(href="#")이 이미 있어 **바이어확인 카드로 즉시 재활용 가능**
- 기한관리 미리보기: `AnonymousHomePreview`(로그인불필요, 현재 DB 0건이라 빈 상태)는 이미 존재 — **샘플데이터 시딩만 하면 됨, 신규개발 아님**. `/procedures` 이하는 로그인 하드게이트 유지.
